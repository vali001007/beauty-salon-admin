>
> 实施边界：不合并开发 `Ami-Brain-证据分散最小修复与防复发方案-2026-08-02.md`；本计划只修复治理中心必需的“候选身份 → 可信 Receipt → 能力治理”闭环

## 1. 执行结论

本次不应重建一套治理中心。当前已经有可复用的数据和页面基础：

- `BrainGovernanceTask` 已有幂等键、状态、租约和重试字段。
- `BrainGateReceipt` 已能保存门禁身份与结果，但可信边界不足。
- `BrainResourceVersion(resourceType=capability_policy)` 已能保存能力策略版本。
- `BrainRelease(scope=governance_policy)` 已与 Runtime Release 隔离发布和回滚。
- 前端已收敛为“治理工作台 / 质量中心 / 策略与发布 / 高级设置”容器页。

改造重点是把当前“全量、串行、人工感知内部任务”的流程转成“变更驱动、证据复用、异常待办、单一灰度序列”。

目标用户流程压缩为四段：

```text
开发 / 提交 PR
  ↓
候选门禁：真实 diff + 必要 Gate + 可信 Receipt
  ↓
变更治理：只处理受影响能力，正常项无感通过
  ↓
发布激活：策略有 diff 才发布新快照，一次审批进入 Shadow
  ↓
自动灰度：Shadow → 5% → 20% → 50% → 100%，异常时人工介入
```

| 复盘结论 | 产品影响 | 改造包 | 前端落点 | 后端/平台落点 | 优先级 |
| --- | --- | --- | --- | --- | --- |

| CLI Receipt 与治理中心断链 | 开发已验证，治理仍显示缺证据 | 可信 Receipt 入库与自动重评 | 显示候选身份和所需 Gate | Receipt Verification、能力映射、任务重调度 | P0 |
| 人工 manage 与机器证据权限混用 | 可能伪造 passed 证据 | 机器证据专用信任边界 | 人工页面不提供“上传可信 passed”能力 | 独立 internal ingest、OIDC/短期签名、服务端重算 | P0 |
| UI V2 未配置即 manage | 灰度失效 | UI fail closed | 未配置默认 Shadow/只读 | 权限和状态保持服务端强校验 | P0 |

| Observe 和同步门禁混用 | 大题库拖慢日常开发 | 非阻断观察调度 | 趋势、失败聚类和告警 | 预算、并发、聚类和观察任务 | P3 |

## 2. 产品目标与非目标

### 2.1 产品目标

1. 开发者不再手工判断应该运行哪些 Brain 脚本。
2. 同一候选身份的 build、类型检查、合同测试和模型评测只执行一次。
3. 能力仍是最小治理单元，支持单个处理，也支持对同一候选批量发起评估。
4. 低风险只读能力在证据可信时自动准入；中风险最多一次人工审批；高/极高风险不进入普通执行白名单。
5. 治理人员默认只看“待我处理”和“当前阻断”，不需要理解分类任务、评估任务和租约等内部编排。
6. 发布人员只看一个 candidate rollout sequence，不再从多组历史 Release 中猜测当前阶段。
7. 策略已发布、Runtime 待接入、Shadow 中、Enforced 必须是清晰分离的状态。
8. 使用端到端耗时、等待证据耗时和等待审批耗时衡量效率，不再用任务快速进入阻塞的 14—16 秒代替治理周期。

### 2.2 非目标

- 不删除历史 Release、Eval Run、Receipt、任务、Gold、报告、轨迹或 Legacy 代码。
- 不直接修改当前 active Runtime Release。
- 不把治理策略发布自动解释为 Runtime 已生效。
- 不放松正式 Release 指纹、Eval evidence、题集、Provider/模型、源码新鲜度、依赖、权限和预热校验。
- 不把人工 `manage` 权限当作机器证据写入权限。
- 不在本计划中扩展多 Release 历史证据整理工程。

## 3. 目标架构

```text

        │
        ▼

  - repository/base/head/merge-base
  - diff/source/release/suite/data/model identity
        │
        ▼
brain:check Gate Orchestrator
  - 影响图
  - 子 Gate Receipt
  - 只重跑失效项
        │ trusted CI ingest
        ▼
Gate Receipt Verification Service
  - CI identity / 签名
  - checksum 重算
  - Eval Run / Release 身份校验
        │
        ├── Governance Task Worker
        │     - 自动分类
        │     - 自动评估
        │     - 证据到位后重新调度
        │
        └── Governance Candidate Read Model
              - 受影响能力
              - 异常待办
              - 策略 diff
              - 发布准备度
                       │
                       ▼
Policy Snapshot Orchestrator
  - 无 diff 复用 active snapshot
  - 有 diff 创建/发布 governance_policy
                       │
                       ▼

  - 晋级、暂停、回滚

```

## 4. 数据模型改造

数据库只采用增量 migration，不执行 reset、drop、truncate 或批量删除。执行 migration 前必须确认 `packages/server-v2/.env` 指向批准的 Supabase 开发库。

### 4.1 新增 `BrainGovernanceCandidate`

该模型表示一个候选变更，不是新的版本中心。

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `candidateKey` | 唯一候选标识，建议为 repository + head commit |
| `repository` | 仓库身份 |
| `eventName` | `pull_request/push/manual` |
| `branch` | 候选分支 |
| `baseCommit` | 比较基线 |
| `mergeBaseCommit` | 实际 merge-base |
| `headCommit` | 候选 commit |
| `changedFilesChecksum` | 变更文件集合指纹 |
| `diffChecksum` | 候选 diff 指纹 |
| `sourceFingerprint` | Brain 源码指纹 |
| `riskLevel` | 本候选最高风险 |
| `status` | `collecting/checking/governing/ready/blocked/releasing/observing/completed/superseded` |
| `policyDecision` | `reuse_active/create_snapshot/blocked` |
| `policySnapshotId` | 复用或新建的策略快照 |
| `rolloutSequenceId` | 灰度序列 |
| `createdAt/updatedAt/completedAt` | 端到端耗时口径 |

索引：

- 唯一：`candidateKey`。
- 普通：`status, updatedAt`。
- 普通：`repository, headCommit`。

### 4.2 扩展 `BrainGateReceipt`

保留当前字段，新增：

| 字段 | 说明 |
| --- | --- |
| `schemaVersion` | 新格式固定为 3；新增 Release 阶段 Eval Run 与 evaluation Release 身份绑定 |
| `candidateId` | 关联候选 |
| `baseCommit/headCommit/mergeBaseCommit` | 禁止脱离候选身份复用 |
| `identityChecksum` | 服务端按规范化 JSON 重算 |
| `issuerType` | `local/ci/service/release_service` |
| `issuer` | workflow、repository 或 service subject |
| `trustLevel` | `untrusted_dev/trusted_candidate/verified_release` |
| `verificationStatus` | `received/verified/rejected/stale` |
| `verificationError` | 验签或身份失败原因 |
| `verifiedAt/ingestedAt` | 入库与验证时间 |
| `evalRunId/evaluationReleaseId` | Release 阶段回溯正式评测 |

兼容规则：历史 receipt 默认 `schemaVersion=1`、`trustLevel=untrusted_dev`，可以查看但不能驱动自动准入。

### 4.5 扩展 `BrainGovernanceTask`

保留当前状态集，增加：

| 字段 | 说明 |
| --- | --- |
| `candidateId` | 所属候选 |
| `receiptId` | 触发评估的 Receipt |
| `blockerType` | `none/evidence/business/system/permission` |
| `blockerCode` | 机器可识别阻断原因 |
| `resolutionType` | `wait_ci/select_store/request_approval/edit_policy/retry_system/contact_owner` |

规则：

- `revision_required + evidence` 不提供通用“重试”。
- Receipt 到位后新建幂等 evaluate 任务，历史阻断任务保留。

- 业务前置条件未满足不消耗 `maxAttempts`。

## 5. 后端详细改造

### 5.1 候选身份服务

新增 `BrainGovernanceCandidateService`：

1. 接收 repository、事件类型、base/head commit、merge-base 和 diff 文件集合。
2. 使用 NUL 分隔解析特殊及中文路径，包含未跟踪文件。
3. 生成 `candidateKey` 并幂等 upsert。
4. Candidate/Release 缺少 base/head/merge-base 时直接 No-Go。
5. 同一 head 但 base 或 merge-base 变化时视为新候选身份。
6. 新 commit 到达后旧候选标记 `superseded`，不删除证据和任务。
7. 提供 Candidate 聚合读模型，避免前端并发拉取多个全量列表再自行拼装。

### 5.2 影响图输出真实能力 key

调整 `ami-brain-check-impact-map.json`：

- 保留 `brain_runtime/brain_actions/brain_governance` 等技术域用于选择 Gate。
- 新增 capability resolver，输出 `appointment_gap_list` 等真实能力 key。
- 从 Skill Registry、Action Binding、Semantic Mapping 和评测题目注册表生成能力映射，避免维护第二份长期手工能力表。
- 无法映射的敏感变更保持 `unclassified/high`，不得自动准入。
- Receipt 同时输出 `domains/capabilities/contracts/gates` 和映射来源规则。

### 5.3 可信 Receipt 服务

拆出 `BrainGateReceiptVerificationService`：

1. `dev` Receipt 只作本地反馈，不用于自动准入。
2. Candidate Receipt 只允许受信 CI/service identity 写入。
3. Release Receipt 只允许 Release/Eval 服务产生，必须关联真实 Eval Run 和 evaluation Release。
4. 后端重算 `identityChecksum/resultChecksum`，不信任请求体自报值。
5. 校验 GitHub OIDC/JWT 的 issuer、audience、repository、workflow、ref 和 head SHA。
6. 若首阶段无法接入 OIDC，可使用后端签发的短期上传 token 过渡；禁止使用前端或长期人工 token。
7. Candidate/Release 缺少 commit、suite、data snapshot、Provider、model 或必要 Release identity 时，只能保存为不可准入证据。
8. 验证失败返回结构化原因，区分业务身份不匹配、权限和系统错误。

新增机器权限：

```text
core:brain-governance:receipt-ingest
```

该权限不出现在普通人工角色勾选列表，只授予 CI/service account 或超级管理员通配。

### 5.4 独立治理任务 Worker

新增 `BrainGovernanceTaskWorkerService`，使用仓库已存在的 `@nestjs/schedule`，第一阶段不引入新队列中间件：

- 每 5 秒批量领取 `pending` 和租约过期任务。
- 使用条件更新保证多实例只有一个 Worker 领取成功。
- 一次最多领取 10 条，写入 owner 和 lease。
- 长任务支持租约续期；进程重启后自动回收过期租约。
- 按 `classify/evaluate` 拆分 handler。
- Controller 不再通过 `void processTask(...)` 触发后台工作。
- 达到最大尝试次数进入 `failed/system` 并记录告警。
- 服务关闭时停止领取新任务。

### 5.5 异常驱动的能力治理

目标流程：

1. Candidate Receipt 验证通过。
2. 根据真实 capability key 查找当前 policy。
3. 未变化的已分类能力继承当前风险和模式。
4. 新能力、权限扩大、规则冲突或无法识别时才创建 classify 异常待办。
5. 可自动分类的能力直接创建 evaluate 任务。
6. 低风险 + readonly + trusted valid Receipt 自动准入。
7. 中风险 + trusted valid Receipt 进入一次人工审批。
8. 高/极高风险强制 `preview/advisory/alert + not_allowed`。
9. 证据缺失进入 `revision_required/evidence`；证据到位后系统自动新建 evaluate。
10. 人工降低风险必须有 approve 权限、理由和原/目标风险审计记录。

批量与单个治理边界：

- 系统可对同一 Candidate 批量发起评估。
- 每个能力仍产生独立 policy version、task 和准入结果。
- 低风险自动结果可批量展示。
- 中风险默认逐能力审批。
- 不在本期默认开放中风险批量准入。

### 5.6 策略快照 diff 与复用

新增 `BrainGovernancePolicyOrchestratorService`：

1. 根据 Candidate 受影响能力与 active policy snapshot 生成 diff。
2. 全部策略 checksum 一致时返回 `reuse_active`，不创建新策略 Release。
3. 有 diff 时创建 `scope=governance_policy` 草稿，列出新增、变更、暂停、证据更新和 Runtime 状态变化。
4. 快照必须覆盖 Runtime Release 所需全部能力，不能发布不可独立运行的局部快照。
5. 发布仍需 `publish` 权限；无 diff 复用不需要再次发布。
6. 策略回滚仍只影响 `governance_policy`，不影响 active Runtime Release。

### 5.7 单一 Rollout Sequence

新增 `BrainRolloutSequenceService`：

- 一个序列组织五个现有 Release 阶段。
- 所有阶段共享 Candidate identity、version map、policy snapshot 和 release fingerprint。
- 只允许当前阶段操作，禁止跳级。
- 发布人员执行一次“校验并激活 Shadow”。
- 后续根据观察窗、错误率、超时率、权限异常、负反馈和业务指标判断晋级。
- 第一版采用“系统给出晋级建议，人工点击晋级”；连续两个候选周期稳定后再开启自动晋级。
- 任一阶段可 pause/rollback。
- 回滚目标必须是序列记录的 previous Runtime Release。
- 不修改当前 active Runtime Release 452，新序列从下一个候选开始使用。

### 5.8 Release 真实证据契约

后端返回 `releaseReadiness`，前端不得再从 Release item snapshot 的 `tests` 字段推断：

```json
{
  "status": "ready|blocked|unavailable",
  "canRelease": true,
  "evaluationReleaseId": 0,
  "evalRunId": 0,
  "releaseFingerprint": "...",
  "suiteChecksum": "...",
  "questionCount": 100,
  "provider": "...",
  "model": "...",
  "generatedAt": "...",
  "expiresAt": "...",
  "blockers": []
}
```

要求：

- active Release 证据读取失败时显示 `unavailable`，不能显示“等待评测门禁”。
- `canRelease=true` 继续由现有严格 Release 校验规则计算。
- 证据与 Candidate/Release 不一致时返回明确 blocker。

### 5.9 治理效率指标

总览接口改为返回：

- Candidate Gate 耗时。
- Receipt 生成到入库耗时。
- 等待证据耗时。
- 等待人工审批耗时。
- Candidate 到 Shadow 端到端耗时。
- Shadow 到 Full 耗时。
- 符合条件的低风险能力自动准入率。
- 首次通过率、重试率、子 Gate 复用率和减少的模型调用量。
- 人工升/降风险改判率。
- 用户问答端到端耗时、首次可见回答耗时、模型耗时和工具/数据耗时的 P50/P95 与样本量。

不再把分类任务与快速进入 `revision_required` 的评估任务混合成一个 P50/P95。

问答耗时必须从 Brain Run/Trace 的服务端时间戳聚合，不由前端以渲染时间估算；缺少某个分解时段时返回 `null + unavailableReason`，不以 `0` 代替。

### 5.10 门店上下文边界

明确两种 scope：

- `global`：Candidate、能力策略、任务、策略快照、Runtime Release。
- `store`：语义数据、门店 Eval Run、记忆和依赖真实门店数据的质量详情。

“全部门店”下：

- 允许查看 global 页面和跨店聚合指标。
- 进入需要 `X-Store-Id` 的详情前要求用户选择单店，不发送必然失败的请求。

## 8. CLI 与 CI 改造

### 8.1 `brain:check`

新增参数：

```text
--repository
--event-name
--base-commit
--head-commit
--merge-base
--candidate-key
--receipt-output
--upload-receipt
--consume-gate-receipt
```

规则：

- dev 允许脏工作树，不上传为可信证据。
- Candidate 必须有 base/head/merge-base。
- Release 必须有干净工作树、完整 Candidate 身份、Release fingerprint 和正式 Eval evidence。
- Observe 定时执行，默认不阻塞日常 Candidate。
- dry-run 即使被阻断也先输出完整计划、预计命令、调用量和 blockers。
- 摘要只显示数量和前若干项，完整文件集合写入 JSON artifact。

### 8.2 GitHub Actions

P0 先修准确性：

1. checkout 获取足够历史以计算 merge-base。
2. PR 使用 base/head SHA；push 使用 before/after SHA。
3. 删除固定 `--scope=packages/server-v2/src/brain/brain.controller.ts`。
4. 生成 Candidate Receipt artifact，并通过 OIDC 或短期 token 上传。
5. 上传失败时不冒充治理闭环完成，但保留 artifact 诊断。

P2 再去重：

- `brain:check` 复用同 pipeline 已完成的 typecheck、build 和合同测试子 Receipt。
- 完整后端测试保留独立 job，但 Candidate Gate 不重复执行已覆盖套件。
- 全量模型评测生成财务、库存、预约等子集视图，不重复调用 Provider。
- 同 `gateKey + identityChecksum` 有效期内只执行一次。

### 8.3 Observe

- `release-core`、`standard-regression` 和 `extended-rotation` 作为夜间或周期观察任务。
- 题数必须每次从 `ami-brain-suite-manifest-v2.json` 动态读取并写入 Receipt/报告，不在 workflow 或脚本中长期硬编码。当前清单为 350/1040/671，后续题集轮换后以 manifest 实际值为准。
- 设置模型调用预算、并发、超时和中止条件。
- 输出失败题簇、新增失败、已恢复、负责人和趋势。
- 使用独立定时 workflow，设置防重入 concurrency group、整体超时、Provider/数据库前置检查、失败告警和明确 owner；不挂入普通 PR required check。
- 一次完整模型运行产生共享原始结果，三个套件只生成结果视图和分类报告，不得为领域子集重复调用 Provider。
- 连续两个 Candidate 周期无 P0/P1 漏检后，再确认其不阻塞普通 Candidate。

- 41 个能力和 83+ 任务都可通过 UI 分页到达。
- 全部门店下不再先发失败请求再显示空表。

### P2：策略复用与单一灰度序列（8—12 人日）

5. 观察阈值校验与晋级建议。

前端：

1. 策略页先显示 diff；无 diff 复用 active snapshot。
2. 运行发布改为一个 sequence 卡片和时间线。
3. 一次“校验并激活 Shadow”。
4. 历史序列折叠。

验收：

- 策略无 diff 不创建新 `governance_policy`。
- 一个 Candidate 只出现一个 rollout sequence。
- 不同序列的阶段不会混入同一时间线。
- 跳级、证据失效、策略漂移和指标超阈值时后端阻断晋级。

4. 治理事件日志、端到端指标和问答耗时聚合 API。
5. 质量中心增加问答耗时拆分、趋势和单位明示展示。
6. 连续两个 Candidate 周期无 P0/P1 漏检。

## 13. 灰度与回滚

### 13.1 上线顺序

1. 只上线 Candidate identity 和 CI 真实 diff，Receipt 仅存档不驱动准入。
2. 开启 Receipt 服务端验证，保持自动准入关闭。
3. UI V2 以 Shadow 只读展示 Candidate、证据和任务建议。
4. 开启 Worker 和 Receipt 到位自动重新调度。
5. 对少量低风险 readonly 能力开启自动准入，不切 Enforced。
6. 开启 Policy diff/reuse 和 Rollout Sequence 只读展示。
7. 新 Candidate 使用 Sequence 激活 Shadow，前两个周期人工点击晋级。
8. 无 P0/P1 漏检且指标可信后，再开启自动晋级和 Observe 非阻塞调度。
9. 最后另行申请 Legacy 代码物理退役，历史数据不删除。

### 13.2 回滚方式

| 风险 | 回滚方式 |
| --- | --- |
| Candidate diff 异常 | 关闭新 diff 分流，恢复旧命令；保留 artifact |
| Receipt 验证异常 | 关闭自动入库/准入，强制旧 Gate 重跑 |
| Worker 异常 | 停止 Worker 调度，保留任务和租约 |
| UI V2 异常 | 将 UI 模式回退 `shadow/legacy` |
| Policy diff 异常 | 停用 prepare/reuse，恢复手工策略快照 |
| Rollout Sequence 异常 | 停止晋级，使用既有 Release 服务回滚 previous Runtime Release |
| Observe 误判 | 将对应题簇临时恢复为阻断项 |

回滚不执行 migration reset，不删除 Candidate、Receipt、Task、Sequence 或历史 Release。

### 18.17 Candidate、Rollout 状态机与发布防绕行最终收口（2026-08-02 第十二轮）

#### 18.17.1 Candidate 与策略状态机

- Policy preview 会阻断未分类、缺失或过期证据、待审批、失败及未完成治理任务。
- Candidate 复用 active 治理策略时转为 `ready`；新策略快照发布后，仅无阻塞任务的关联 Candidate 转为 `ready`。
- 只有 `ready` Candidate 可创建 Rollout Sequence；创建后依次进入 `releasing`、`observing`，Full 完成后进入 `completed`。
- 回滚后 Candidate 转为 `blocked` 并记录完成时间，不再错误保留为 `observing`。
- 前端创建序列下拉框只展示 `ready` Candidate，避免绕过后端状态机。

#### 18.17.2 Rollout Sequence 发布防绕行

- Sequence 拥有的 Release 禁止通过旧单 Release 接口直接激活、驳回或回滚。
- Sequence 内部激活必须携带 `sequenceId/fromStage/toStage`，且只能进入紧邻下一阶段，不能从 Shadow 跳到 20% 或更高阶段。
- Rollback 必须恢复 `previousRuntimeReleaseId`，即 Candidate 开始前记录的 Runtime 基线；回滚目标不一致时后端拒绝。
- 旧 baseline/rules 回滚入口不能绕过 Sequence 控制。
- 当前序列和 `completed/rolled_back/superseded` 历史序列在前端分开展示，历史序列不进入当前审批队列。

#### 18.17.3 暂停态不再成为操作死路

代码复核发现，原暂停操作刷新页面后既不能恢复，也会失去回滚入口。现已补齐：

```text
draft/active -> paused
paused + 当前阶段未激活 -> resume -> draft/releasing
paused + 当前阶段已激活 -> resume -> active/observing
paused + 当前阶段已激活 -> rollback -> rolled_back/blocked
```

新增 `POST /brain/governance/rollout-sequences/:id/resume`，继续使用独立 `release` 权限；暂停态仍可安全回滚到 Candidate 前 Runtime。前端增加“恢复”按钮，并明确回滚目标不是上一灰度阶段，而是 Candidate 前 Runtime Release。

本轮使用最新生产编译产物、本地 58081 端口和批准的 Supabase 开发库执行真实 HTTP 权限矩阵。验收没有使用 Controller 直调或 Mock 权限，而是创建带唯一时间戳的临时角色和用户，通过真实登录、JWT、CSRF 中间件、权限 Guard、Controller 和 Service 调用链验证。

#### 18.20.1 发现并修复的 P0 缺陷

首次真实矩阵中，所有治理 POST 即使具备正确权限也返回 403。核对响应链路后确认是 CSRF 中间件先于权限 Guard 拦截；人工页面请求可以获取并携带 CSRF Cookie/Header，因此这不是权限实现缺陷。

但同一规则还错误拦截了：

```text
POST /api/brain/governance/internal/gate-receipts
```

该接口由 GitHub Actions 或发布服务通过 OIDC/HMAC 调用，不存在浏览器 CSRF Cookie。若不修复，远程可信 Receipt 即使 OIDC 配置完全正确，也会在进入 `BrainGovernanceReceiptIngestGuard` 前被 403 拒绝，导致 Candidate、Worker 自动重评和低风险准入永远无法形成真实闭环。

修复方式：

- CSRF 中间件只对上述精确路径豁免，不使用宽泛的 `/api/brain/governance/internal` 前缀。
- 查询参数不影响精确路径识别。
- 相似伪造路径如 `gate-receipts-forged` 仍必须提供有效 CSRF。
- Receipt 接口的真实信任边界仍由 GitHub OIDC 或显式 HMAC fallback Guard 承担；人工 JWT 不会因 CSRF 豁免获得写入权限。

新增 CSRF 定向测试覆盖精确豁免和相似路径拒绝，4/4 通过。

### 18.22 Worker 租约 fencing 与 Rollout Sequence 残缺恢复（2026-08-02 第十七轮）

在按 DoD 逐项审计多实例和发布恢复链路时，发现两个自动化原未覆盖的高风险窗口。

#### 18.22.1 失去租约的 Worker 不得继续回写

原实现只在任务领取时使用条件更新；后续 `classifying/evaluating`、完成、业务阻塞和系统失败回写仅按任务 ID 更新。如旧 Worker 在租约过期后恢复，可能覆盖新 Worker 的处理结果。

现已收口为：

- 所有运行中状态迁移、完成、阻塞和失败回写均必须同时匹配 `taskId + leaseOwner + 未过期 lease + 运行中状态`。
- 进入 `classifying/evaluating` 时同步延长租约，保证当前短任务处理窗口。
- 一旦租约不属于当前 Worker，立即停止处理，不创建策略版本，也不把新 Worker 状态覆盖为失败或重试。
- 新增定向测试模拟“领取后租约已由另一 Worker 持有”，验证旧 Worker 返回 `false` 且无策略副作用。

#### 18.22.2 残缺 Rollout Sequence 可幂等续建

原创建流程会先创建 Sequence，再依次创建 Shadow、5%、20%、50%、100% 五个 Release。若进程在中途退出，重试时因 Candidate 已有 Sequence 而直接返回，会产生无法发布的残缺序列。

现已改为：

- 只有五个标准阶段都存在时才直接复用已有 Sequence。
- 如 Sequence 或 Release 只创建了一部分，重试会按原 Candidate、策略快照、治理模式、Release key、阶段和资源版本集合校验后续建缺失阶段。
- 如 Release 已落库但未完成 Sequence 关联，可在身份完全一致时恢复关联。
- 同名 Release 的 Candidate、Sequence、阶段或资源集合不一致时 fail closed，不拼接历史或其他候选证据。
- 并发续建遇到唯一键竞争时，重新读取并验证已落库 Release，避免同一候选因短暂竞争留下残缺序列。
