## 3. 本轮新增完成项

### 3.1 查询版产品画像

- 固化 `query_only_v1`。
- 白名单固定为 33 项只读、无副作用能力。
- 8 项 Action 能力不进入查询版规划与执行范围。
- 产品画像进入 Release fingerprint；Release 创建、激活和运行选择均校验画像。

产品价值：首轮试运行的风险面从“AI 可能修改业务数据”收敛为“AI 只读查询可能答错或答慢”，事故半径明显降低。

### 3.2 Action 服务端硬边界

- preview、confirm、retry 均受 Release 策略与部署总开关双重约束。
- 拒绝发生在 Gateway、事务、执行记录和外部调用之前。
- 稳定错误码为 `brain_action_execution_disabled_by_release_profile`。
- 拒绝写入治理 trace，便于审计误调用来源。
- 示例部署配置已默认 `BRAIN_ACTION_EXECUTION_ENABLED=false`。

产品价值：即使旧客户端、历史 actionId、重放请求或错误 Release 路由仍发送写请求，也不能产生业务写入。

### 3.3 三端响应合同

- 服务端返回 `productProfile` 和 `actionsEnabled`。
- 查询版响应出口会剥离 Action preview。
- 管理端历史 Action 卡禁用执行和重试。
- 移动端、Aura Lite 不再展示或映射查询版 Action。

产品价值：三端体验与服务端策略一致，减少“界面显示可执行、服务端实际拒绝”的用户困惑。

### 3.4 Release-stage 部署健康门禁

当 `BRAIN_RELEASE_STAGE=release` 时，health/ready 强制要求：

- commit、branch、buildId、environment 非空。
- provider、model、timeout、fallbackPolicy 非空。
- 部署实际数据库目标的 protocol、host、port、database、schema 完整，且不包含用户名或密码。
- 目标门店/用户真实命中指定 Release。
- Release fingerprint 与 `query_only_v1` 一致。
- `actionsEnabled=false` 且部署总开关关闭。

产品价值：不再允许“服务返回 200，但不知道部署了哪个版本”被误判为发布成功。

### 3.5 同候选证据身份

- `candidateId` 由产品画像、runtime commit、diff、Release、数据快照、题集、provider/model、超时、fallback、部署、数据库目标和门店身份共同计算。
- candidate lock 必须绑定当前 HEAD；HEAD 漂移立即失败。
- release stage 缺 candidate lock 直接阻断。
- 即使候选没有变更文件，也固定执行 `release_candidate_close`，不会退化为普通单测。
- release receipt 必须携带完全一致且非空的 `candidateId`；旧的空 candidateId receipt 不可复用、不可上传为 verified release。
- 八类 evidence receipt 只能在同一 candidateId 下聚合。
- evidence type 和 status 使用固定白名单；每个 artifact 都必须记录 SHA-256，`resultChecksum` 绑定 candidateId、证据类型、状态和全部 artifact checksum。
- `brain:release:candidate receipt` 从仓库内实际文件字节生成 receipt；close 时重新读取文件，缺失、篡改或 symlink 逃逸均 fail-closed。
- 四类半自动证据必须包含 reviewer、角色、trace、账号、业务角色、门店、运行和截图/录像上下文，review media 必须同时是已校验 artifact。
- 自动证据不再只相信手填状态：Release contract、正式 100 Gold、固定 60 题和目标库报告均校验内容与候选身份；diagnostic Gold 明确禁止进入 `gold_100`。
- 四类半自动证据也必须满足机器可读合同：`super_admin` 加七个活跃 Brain 角色必须逐身份覆盖且四类风险计数为 0；三端 E2E 必须逐端覆盖 11 类旅程；provider/fallback 必须覆盖五类故障；rollback 必须证明阈值、自动暂停、shadow/小流量 canary 和回滚后 Action 关闭。
- 新增 `brain:release:candidate template`，从 candidate lock 生成默认 blocked 的候选绑定模板；未填写完整的模板不能被误签为 passed receipt。
- evidence receipt 升级为 `ami-brain-evidence-receipt/v2`：checksum 同时绑定有效期、reviewer、reviewer role、trace 和全部 review context；最终 close 不只复核文件 SHA-256，还会重新执行八类 artifact 内容与候选身份校验，手工构造自洽 checksum 也不能绕过。
- 单项证据最长有效 168 小时；最终 eligibility 继承八项证据中最早的到期时间，不再固定延长为 30 天。

产品价值：禁止把历史 Release、旧模型、旧数据、旧题集和不同客户端证据拼接成一份“看似全绿”的上线报告。

## 6. 推荐的最小试运行方式

- 范围：1 家内部或友好门店。
- 用户：5—10 个真实用户。
- 周期：7 天。
- 产品画像：`query_only_v1`。
- Action：服务端与部署总开关双关闭。
- 放量：Go 前完成 shadow/5% canary 回滚演练；Go 后再按 5% → 20% → 50% → 100% 的试运行人群逐级观察。

试运行成功标准：

- 安全：0 跨店、0 越权、0 误写入、0 假成功。
- 正确：高频经营问题事实和口径可接受。
- 稳定：无长期 running，异常有明确降级。
- 性能：固定 60 题和真实流量 P95 达标。
- 体验：三端澄清、多轮、失败状态一致。
- 运维：每个请求能追溯到用户、门店、candidateId、Release、provider/model 和结果。

不建议首轮同时开放 Action。如果产品要求“查询 + Action”一起试运行，还必须新增真实业务动作的 preview → confirm → execute → receipt、幂等、取消/重试、部分失败恢复和业务对账验收。

## 7. 推荐执行顺序

1. 人工审查混合工作区并确定明确提交切片。
2. 经授权后形成干净 commit、新 query-only Release 和真实部署。
3. 锁定 candidateId。
4. 并行执行 100 Gold、八身份权限、固定 60 题和三端 E2E。
5. 完成目标库、provider 故障、监控与回滚演练。
6. 聚合八类 receipt，运行 candidate close。
7. `releaseEligible=true` 后召开 Go/No-Go 评审，再启动 1 店 7 天试运行。
