# Ami Brain 治理与发布门禁裁剪方案

> 日期：2026-08-01
> 文档性质：基于当前仓库的治理裁剪决策与实施方案
> 本轮范围：Brain 治理中心前端页面、治理流程、测试分层、发布门禁、证据管理和开发体验
> 本轮不包含：直接修改运行代码、数据库、active Release 或生产配置

## 1. 决策结论

当前 Ami Brain 确实存在治理冗长、门禁混层和重复验证，但问题不是“安全要求都太高”，而是以下四类任务被当成了同一种流程：

1. 开发者修改一段代码后的快速反馈。
2. 候选版本是否值得进入人工验证。
3. 正式发布是否满足产品签收条件。
4. 历史审计和过程报告是否完整。

结果是低风险只读修改也被迫承担接近正式发布的验证节奏，而同一结论又被单测、定向题、子集、全量题、验收脚本和人工报告重复证明。

推荐采用“一个入口、四个阶段、四级风险、一次正式签收”的裁剪方案：

```text
变更影响分析
→ D 开发门禁：只验证受影响代码和 2—5 道代表题
→ C 候选门禁：验证受影响失败簇、合同和候选身份
→ R 发布门禁：冻结候选后只执行一次正式签收
→ O 观察任务：大题库、轮换题和历史审计异步运行，不阻塞日常开发
```

前端同步从“9 个技术模块平铺”改成“治理总览 + 能力治理 + 治理任务 + 策略快照”的异常驱动工作台。治理人员默认只处理待分类、待审批、需修订和运行待接入事项，不再在技能、语义、评测和发布页面之间人工拼接结论。

裁剪原则：

- 裁剪重复执行，不裁剪安全结论。
- 低风险只读能力快速通过，高风险写操作继续严格验证。
- 同一候选、同一输入、同一结论只生成一份有效证据。
- 开发验证允许绑定脏工作树差异指纹；正式激活仍必须绑定干净提交和部署身份。
- 不批量删除现有报告和历史题集，先冻结新增方式并建立索引。

包含前端工作台后，完整方案预估从原先偏后端的 13—21 人日修正为 30—39 人日；一名前端和一名后端并行时，预计 3—4 周。

当前全领域 manifest 同时维护：

- `releaseCore`：350 题。
- `standardRegression`：1040 题。
- `extendedRotation`：671 题。
- `evidenceReviewRequired`：284 题。

与此同时，2026-08-01 的最小门禁交付口径已把完整 100 题事实和固定 60 题性能后移，本轮仅以预约/库存 7 道 Gold 代表题、相关单测和后端构建完成“可人工接入”验证。

这说明当前不是缺少测试，而是缺少统一的“什么结果对应什么产品状态”定义。

## 3. 根因判断

### 3.1 门禁等级和产品状态没有一一对应

“单测通过”“代表题通过”“Gold 子集通过”“100 题通过”“350/1040 题通过”“正式激活”同时出现，但没有统一映射到以下产品状态：

- 开发中。
- 可合并。
- 可人工验证。
- 可灰度。
- 可正式激活。

因此局部成功容易被误报为正式完成，正式发布要求又会反向侵入每一次日常修改。

### 3.2 证据失效范围过大

当前很多流程隐含采用“任何代码变化，全部证据失效”的策略。实际上：

- 文案变化不应作废数据库事实证据。
- 只读查询修复不应作废六项写操作验收。
- 财务 resolver 修改不应重跑库存、营销和跨端全部链路。
- 纯性能调度修改不应强制作废已经确认的结构化事实结果。

### 3.3 正式发布条件被用于开发阶段

现有 Release acceptance preflight 会检查干净工作树、提交身份、部署健康、跨端合同和 Action Release Contract。正式激活需要这些条件是合理的，但开发者在脏工作树中做定向验证时不应被这些条件阻断。

### 3.4 测试套件按来源累加，没有按结论去重

同一道能力可能同时存在于：

- 单元测试。
- 定向题。
- 失败簇子集。
- 财务/库存等领域子集。
- 100 题 Gold。
- 350 题 release-core。
- 1040 题 standard-regression。
- 671 题轮换集。

这些套件可以保留不同观察价值，但不能都作为同一次发布的独立阻断项，也不应重复调用模型后再分别汇总。

### 3.5 报告承担了流程状态功能

当前通过不断新增 Markdown 报告表达“最新一次执行到了哪里”。报告适合签收和复盘，不适合充当任务状态机。其后果是最新口径难找、同一问题产生多版报告、人工需要从文件名推断当前状态。

### 3.6 不是从零开始，但现有能力尚未形成闭环

当前已经可以复用的基础包括：

- Release acceptance 已支持 checkpoint/resume。
- 性能验收已提供 `--diagnostic-only`，可避免正式激活 preflight 的重复执行。
- release-core 结果可以生成历史子集视图。
- 已有最小门禁、失败簇收敛和四级能力治理文档。

当前缺口是：没有统一 `brain:check` 入口，没有基于变更范围的自动分流，没有可复用的门禁 receipt，开发态仍未与正式激活的干净提交/生产健康条件彻底分离。因此本方案优先整合已有能力，不再新增另一套平行治理体系。

## 4. 目标治理模型

### 4.1 四阶段门禁

| 阶段 | 目的 | 默认执行内容 | 是否阻断正式发布 |
| --- | --- | --- | --- |
| D：开发门禁 | 快速发现本次修改是否明显有误 | 影响分析、受影响单测、定向静态检查、2—5 道代表题 | 否，只阻断当前开发批次 |
| C：候选门禁 | 判断是否值得进入人工验证或候选冻结 | 受影响失败簇、合同、权限/跨店反例、候选 warmup、构建 | 否，只决定候选是否可进入下一阶段 |
| R：发布门禁 | 对冻结候选做一次正式产品签收 | 100 题事实、60 题性能、变更涉及的跨端/动作/迁移门禁、发布身份和回滚检查 | 是 |
| O：观察任务 | 发现长尾回归和题库漂移 | 350/1040/671 题、历史题库对照、趋势和误报分析 | 默认不阻断；发现 P0/P1 问题后升级处理 |

说明：

- 现有 350/1040/671 题先转为 O 观察任务，连续两个正式候选周期对比无重大漏检后，再决定是否永久取消其发布阻断地位。
- 100 题事实与 60 题性能沿用当前已形成的正式签收口径，但每个冻结候选只运行一次。
- 代表题、领域子集和失败簇只作为 D/C 的早停工具，不再计为新的产品门禁。

### 4.2 四级风险分流

| 风险级别 | 能力类型 | D/C 阶段策略 | R 阶段必须保留 |
| --- | --- | --- | --- |
| A 低风险 | 查询、列表、统计、明细 | 自动影响分析、定向事实题、权限和跨店反例 | 事实正确、权限边界、空结果、性能 |
| B 中风险 | 复杂分析、风险判断、草稿/预览 | 领域 Gold、边界数据、一次人工审批 | 口径、解释边界、误报漏报、审批证据 |
| C 高风险 | 库存、价格、资金、正式业务状态变更 | 不进入自动执行快速通道，只做预览或提示 | 权限、确认、幂等、write-set、回执、真实链路 |
| D 极高风险 | 权限、批量删除、资金冲正、敏感导出 | 仅告警和人工处理，不进入普通能力发布 | 不提供普通自动执行入口 |

低风险能力不再逐步人工点击校验、评估、审批和启用；异常才进入人工复核。高风险能力不能因为治理提效而降级。

## 5. 立即裁剪清单

### 5.1 立即停止的重复执行

1. 执行 `build` 后，相邻步骤不再重复同一 tsconfig 的 `tsc --noEmit`。
2. 执行统一跨端合同后，不再单独重跑其已经包含的代表测试和类型检查。
3. 执行 `brain:release:acceptance:test` 后，不再单独重复其中已经编排的题目治理和 Node 合同测试。
4. 财务 22 题、库存子集等如果完全包含在同一次 100 题运行中，只生成子集视图，不再次调用模型。
5. 只读问数修改未触及 Action、回执、write-set、migration 时，不重跑六动作真实验收和迁移门禁。
6. 跨端响应合同未变化时，不重跑三端合同。
7. 同一候选身份下的中断使用 checkpoint/resume，不从第一题重新运行。
8. 不再为每次单题或小簇诊断生成一份独立正式 Markdown 验收报告。

### 5.2 从阻断项降为观察项

- 350 题 release-core。
- 1040 题 standard-regression。
- 671 题 extended rotation。
- 已明确为 `evidence_review_required`、`next_iteration_feature` 或口径未冻结的题。
- 历史 Agent V1—V6 题集对当前 Ami Brain 的兼容性扫描。

这些测试仍可按夜间、每周或候选冻结后的异步任务运行，但不进入普通修改和人工接入的通过率分母。

### 5.3 绝不能裁剪

- 登录角色、权限、门店和跨组织隔离。
- 敏感字段脱敏和导出限制。
- 写操作确认、幂等、并发、write-set、业务 Effect 和 Mutation Receipt。
- 真实业务数据口径与独立 Gold 比较。
- Release、代码、题集、模型和数据快照身份绑定。
- active Release 预热、激活失败阻断和回滚能力。
- Provider 不可用、超时或 fallback 失败的显式标记；不得把基础设施失败计为功能通过。

## 6. 单一入口与证据复用

建议最终收敛为一个入口：

```bash
npm run brain:check -- --stage=dev
npm run brain:check -- --stage=candidate
npm run brain:check -- --stage=release
```

统一入口自动完成：

1. 读取 Git diff 和显式范围，计算受影响模块、能力、合同和题目。
2. 自动判定风险级别，无法判定时升级而不是默认低风险。
3. 生成本轮执行计划，先展示预计命令、模型调用量和阻断项。
4. 复用候选身份未变化的有效证据。
5. 只执行失效的门禁。
6. 输出一份机器可读 receipt 和一份最新摘要。

### 6.1 证据身份

每份证据至少绑定：

```text
stage
riskLevel
changedFilesChecksum
sourceFingerprint
releaseFingerprint
suiteChecksum
dataSnapshot
provider/model/timeout
resultChecksum
createdAt
expiresAt
```

### 6.2 开发候选与正式激活分开

开发和候选阶段允许：

- 工作树未提交。
- 使用 `changedFilesChecksum + diffChecksum` 标识源码身份。
- 使用本地或 evaluation-only Release。
- 不要求 production health URL。

正式发布阶段继续要求：

- 干净提交。
- HEAD、候选 Release 和部署 commit 一致。
- 正式健康检查通过。
- 完整回滚信息存在。

这能解除 vibe coding 过程中最常见的无效阻断，同时不降低生产激活安全性。

## 7. Brain 治理中心前端页面方案

上一版只在实施计划中写了“页面收敛”，不足以指导前端开发。本节将治理中心前端纳入主方案；更完整的页面字段和交互稿可参考 [Brain 治理中心前端改造方案](./Brain治理中心前端改造方案.md)。

### 7.1 当前前端基线

当前 `BrainGovernanceCenter.tsx` 主要负责按路由切换组件，治理中心平铺了 9 个技术模块：

```text
模型规划 / 语义治理 / 角色治理 / 技能治理 / 记忆治理
巡检治理 / 评测中心 / 发布中心 / 反馈指标
```

当前事实：

- `/brain-governance` 默认跳转“模型规划”，不是治理总览。
- 左侧导航把 9 个技术模块全部作为同级菜单，产品操作路径较长。
- 技能、语义、评测和运行发布分别维护自己的列表、弹窗、加载状态和错误反馈。
- 技能页面仍以“启用/停用”为主要操作，容易与风险白名单、正式运行生效混淆。
- 当前权限只有 `core:brain-governance:view/manage`，没有审批和发布职责分离。
- 现有 API 已覆盖角色、技能、语义、巡检、评测、运行 Release、反馈和记忆，但没有完整的治理任务、能力白名单和治理策略快照前端合同。
- 已有页面测试覆盖治理中心路由切换、技能、角色、语义和运行发布轮询，可作为改造回归基线。

因此，前端问题不是“再加几个页面”，而是要从技术模块浏览器改成异常驱动的治理工作台。

### 7.2 目标信息架构

| 一级页面 | 产品定位 | 用户主要任务 |
| --- | --- | --- |
| 治理总览 | 默认首页 | 查看风险分布、待办、过期白名单、运行待接入和治理效率 |
| 能力治理 | 核心工作台 | 分类、评估、白名单、负责人、权限依赖和历史版本 |
| 语义治理 | 业务口径 | 管理指标、实体、关系、维度和动作，查看影响能力 |
| 治理任务 | 统一流程中心 | 查看校验、分类、评估、审批、修订、失败和重试 |
| 策略快照 | 治理发布 | 比较、发布和回滚风险/白名单策略快照 |
| 角色治理 | 角色配置 | 管理角色能力范围和知识范围 |
| 评测中心 | 证据查看 | 查看 D/C/R/O 阶段证据，不重复触发同一评测 |
| 运行发布（现有） | Brain Release | 管理运行 Resource Version、激活和规则回滚 |
| 高级治理 | 低频工具 | 模型规划、记忆、巡检和反馈指标 |

建议路由：

```text
/brain-governance/overview

/brain-governance/semantic
/brain-governance/tasks
/brain-governance/policy-snapshots
/brain-governance/roles
/brain-governance/eval
/brain-governance/runtime-releases

# 兼容一个版本周期
/brain-governance/skills      -> 能力治理或只读兼容页

/brain-governance/planning
/brain-governance/memory

```

默认入口由“模型规划”调整为“治理总览”。旧链接至少保留一个版本周期，避免收藏、文档和历史操作入口失效。

### 7.3 治理总览页面

总览只回答四个产品问题：

1. 当前有什么需要我处理。
2. 哪些能力存在风险或即将失效。
3. 最新治理策略是否已经发布。
4. 策略是否已经被运行侧接入。

首屏建议包含：

- 待分类、待评估、待审批、需修订数量。
- 低/中/高/极高风险分布。
- 只读白名单、预览白名单、提示目录和暂停/过期数量。
- “策略已发布、运行待接入”数量。
- 我的治理待办与主要阻塞原因。
- 最新策略快照、现有运行 Release 和二者是否一致。
- 最近 7 天治理耗时、自动准入率和人工改判率。

指标卡必须能跳转到带筛选条件的能力治理或任务页面。没有数据时显示空态，不用虚构的 0% 改善填充页面。

### 7.4 能力治理页面

主列表从“技能是否启用”改为“能力是否具备治理准入条件”。核心字段：

| 字段 | 展示内容 |
| --- | --- |
| 能力 | 名称、capabilityKey、版本、业务领域 |
| 风险 | 低/中/高/极高/待分类及分类原因摘要 |
| 治理模式 | 只读/预览/提示/告警 |
| 白名单 | 未准入/待审批/已准入/暂停/过期 |
| 评测证据 | D/C/R/O 最新结果、证据时间和是否失效 |
| 运行接入 | 待接入/Shadow/已接入 |
| 权限范围 | 权限码、角色、门店和敏感数据摘要 |
| 负责人 | 业务负责人、治理负责人 |
| 操作 | 查看详情、分类/复核、发起评估、审批历史 |

交互约束：

- 筛选条件同步 URL query，刷新和分享后可恢复。
- 详情使用右侧抽屉，保留列表筛选、分页和滚动位置。
- 低风险自动准入只展示结果和异常，不要求人工逐步点击。
- 人工降低风险等级必须填写理由，并要求 `approve` 权限。
- 高风险不能选择执行白名单；极高风险只能选择告警/人工处理。
- 本阶段只允许批量分配负责人、发起评估和导出，不允许批量降级风险或加入白名单。

### 7.5 治理任务中心

所有长任务统一返回 `taskId`，由治理任务中心展示状态，页面组件不再各自实现轮询协议。

统一状态：

```text
待处理 -> 校验中 -> 分类中 -> 评估中 -> 待审批
        -> 需修订 / 已准入 / 已拒绝 / 已取消
```

页面必须区分：

- 系统错误：接口失败、超时、任务租约失败、Provider 不可用。
- 业务阻塞：缺证据、评估失败、风险无法确认、权限码未登记、口径未发布。

允许操作：查看步骤、重试可恢复步骤、退回修订、审批和取消未发布任务。不可恢复失败必须明确告诉用户需要修改什么，而不是只显示“失败”。

### 7.6 策略快照与运行发布分开

前端必须明确区分两个对象：

| 页面 | 管理对象 | 用户看到的生效含义 |
| --- | --- | --- |
| 策略快照 | 风险等级、治理模式、白名单、审批和评估指纹 | 治理规则已发布，不代表运行已经接入 |
| 运行发布（现有） | Brain Resource Version 和运行 Release | 当前运行时实际生效状态 |

策略快照发布确认至少展示：

- 受影响能力数量。
- 风险升级和降级清单。
- 新增及移出白名单清单。
- 未评估、已过期和运行待接入数量。
- 与上一快照的差异。
- 明确提示“发布治理策略不会自动改变当前 Brain 运行”。

运行发布页保留现有激活、驳回、修改要求、规则回滚和 regeneration job 处理，但菜单和页面标题改为“运行发布（现有）”，避免与策略快照混淆。

### 7.7 前端状态和接口合同

建议新增稳定类型：

```ts
type BrainGovernanceRiskLevel = 'low' | 'medium' | 'high' | 'critical' | 'unclassified';
type BrainGovernanceMode = 'readonly' | 'preview' | 'advisory' | 'alert';
type BrainWhitelistStatus = 'not_allowed' | 'pending' | 'approved' | 'suspended' | 'expired';
type BrainRuntimeEnforcementStatus = 'pending_runtime' | 'shadow' | 'enforced';
type BrainGovernanceTaskStatus =
  | 'pending' | 'validating' | 'classifying' | 'evaluating' | 'pending_approval'
  | 'revision_required' | 'approved' | 'rejected' | 'cancelled';
```

后端需要提供或整合以下前端合同：

```text
GET  /brain/governance/overview
GET  /brain/governance/capability-policies
GET  /brain/governance/capability-policies/:key
POST /brain/governance/capability-policies/:key/classify
POST /brain/governance/capability-policies/:key/evaluate
POST /brain/governance/capability-policies/:key/approve

GET  /brain/governance/tasks/:id

POST /brain/governance/policy-snapshots/:id/rollback
```

优先扩展现有 Resource Version、Release 和治理接口，不新建第二套平行版本中心。列表接口必须支持分页、筛选和 summary 模式，禁止前端拉取全量 snapshot 后自行聚合。

### 7.8 前端权限和交互门禁

权限建议拆分：

| 权限 | 前端能力 |
| --- | --- |
| `core:brain-governance:view` | 查看治理数据和证据 |
| `core:brain-governance:manage` | 编辑分类、负责人、发起评估和退回修订 |
| `core:brain-governance:approve` | 审批中风险、高风险和风险降级 |
| `core:brain-governance:publish` | 发布和回滚治理策略快照 |
| `core:brain-governance:release` | 激活、驳回和回滚正式运行 Release |

页面禁用按钮不是安全边界；后端必须执行相同权限与状态校验。审批和发布权限未拆分前，新页面只能以只读/shadow 方式上线，不应让同一 `manage` 权限同时完成创建、审批和发布。

### 7.9 前端页面验收

前端验收至少覆盖：

- 默认进入治理总览，而不是模型规划。
- 总览待办可以跳到正确筛选结果。
- 能力列表可同时查看风险、白名单、评测证据和运行接入状态。
- “策略已发布”和“运行已生效”不会混为一个状态。
- 高风险/极高风险页面没有进入普通执行白名单的入口。
- 无 `approve/publish/release` 权限的用户看不到或无法执行对应操作。
- 旧 `/skills`、`/release` 链接保持兼容。
- 路由切换继续取消上一页面未完成的治理读取，避免重复请求和旧数据覆盖。
- 1512×746 和 390×844 视口无横向溢出，风险状态不只依赖颜色表达。
- 组件、页面和 E2E 测试分别覆盖空态、加载、失败、审批、发布、回滚和权限拒绝。

## 8. 测试套件去重规则

每道题建立唯一稳定 ID 和覆盖签名：

```text
capability + metric/entity + dimensions + filters + time semantics
+ permission/store scope + expected answer shape + risk level
```

规则如下：

1. 一道题只能属于一个“主阻断套件”。
2. 其他套件只能引用该题结果或生成视图，不能重复运行后分别计数。
3. 同覆盖签名的模板题保留一题作为阻断题，其余进入轮换观察池。
4. 事实题使用确定性字段比较；开放式解释才使用模型 Judge。
5. 口径未冻结、入口缺失或数据证据不足的题不进入正式分母。
6. 题目变更、Gold 变更和运行时变更分别记录，避免把评测器问题误判为产品问题。

## 9. 报告与文档治理

本方案不批量删除现有文件。先执行以下非破坏性治理：

- 当前主线只保留一个“当前门禁口径”文档和一个“当前发布证据索引”。
- 单题、失败簇和重试过程默认只写 JSON/日志到 `outputs/` 或测试数据运行目录。
- 同一任务只维护一个 `latest-summary.md`，新运行覆盖摘要但保留底层不可变证据。
- 只有正式候选签收、重大事故复盘和治理规则变更才新增长期 Markdown 文档。
- 历史报告先标记为 archive，不移动、不删除；后续如需批量整理再单独授权。

## 11. 发布、灰度与回滚

### 11.1 灰度顺序

1. `shadow`：新编排只生成建议执行计划，旧流程仍是最终依据。
2. `dev enabled`：仅 D 阶段使用新入口，结果与旧手工流程对比。
3. `candidate enabled`：A 类只读能力启用 C 阶段证据复用。
4. `ui shadow`：新治理中心只读展示总览、能力和任务数据，旧页面仍可访问。
5. `ui manage`：开放分类、评估和修订；审批/发布按钮仍按权限和后端状态门禁控制。
6. `release observe`：R 阶段仍运行旧正式门禁，同时观察 O 大题库漏检情况。
7. 连续两个候选周期无 P0/P1 漏检、且前端 E2E 无权限越界后，正式将 350/1040/671 固定为观察任务，并把总览设为默认入口。

### 11.2 回滚

- 关闭新 `brain:check` 分流，恢复现有命令入口。
- 关闭 `BRAIN_GOVERNANCE_UI_V2`，恢复旧治理导航和页面；新治理数据、任务和审计记录保留。
- 忽略 receipt/cache，强制重跑原门禁。
- A 类自动准入关闭后恢复人工审核。
- O 观察任务发现重大漏检时，可临时恢复对应题簇为 R 阻断项。
- 前端发布回滚不修改 active Release、Ami Core 权限和历史证据。

## 12. 验收指标

### 效率指标

- 日常只读修改 D 阶段 P50 不超过 5 分钟，P95 不超过 10 分钟。
- 普通候选 C 阶段 P50 不超过 20 分钟，远程模型或供应商等待单独统计。
- 开发者从修改到人工验证最多使用 2 个命令。
- 相同候选、相同输入的重复测试执行次数为 0。
- 非正式阶段的模型评测调用量相比当前人工全链路降低至少 80%。
- 单题/小簇诊断新增长期 Markdown 报告数量降低至少 90%。

### 质量指标

- 权限、跨店、敏感数据和写操作安全漏检为 0。
- 正式 R 阶段的 100 题事实错误为 0。
- 60 题性能达到当前签收阈值，Provider 不可用单独阻断或标记。
- 连续两个候选周期中，O 观察任务未发现被 D/C/R 漏掉的 P0/P1 回归。
- 所有正式发布证据均能追溯到代码、Release、题集、数据和模型身份。

### 前端指标

- 治理总览首屏在汇总 API 正常时 P95 不超过 2 秒。
- 路由切换不会重复拉取同一 summary，也不会出现旧请求覆盖新筛选结果。
- 关键治理操作最多经过一个详情抽屉和一个确认弹窗，不再跨 3 个以上页面拼接证据。
- 具备 `view` 权限但没有 `manage/approve/publish/release` 的账号不能执行越权操作。
- 桌面和 390×844 小屏均无横向溢出，风险和运行接入状态不只依赖颜色。
- “策略已发布、运行待接入”被用户误认为“运行已生效”的验收问题为 0。

## 13. 建议本周立即执行的产品决策

建议本周先批准以下七项，不等待完整治理平台改造：

1. 正式确认 D/C/R/O 四阶段和对应产品状态。
2. 将 350/1040/671 题改为观察任务，先 shadow 两个候选周期。
3. 明确正式签收只保留一次 100 题事实、一次 60 题性能和“按变更触发”的专项安全门禁。
4. 允许开发/候选验证使用 diff fingerprint，正式激活才要求干净提交和部署一致。
5. 停止为每次小簇诊断新增正式验收报告，改用单一 latest 摘要和不可变底层证据。
6. 将治理中心默认入口改为“治理总览”，新增能力治理、治理任务和策略快照三个产品页面；旧技能治理和运行发布保留兼容期。
7. 在开放审批、策略发布和运行 Release UI 前，先拆分 `approve/publish/release` 权限；权限未拆分时只能上线只读/shadow 页面。

这七项不需要删除测试、不需要降低权限、不需要修改 active Release，即可先消除大部分重复操作和治理噪音；其中新增页面需要配套 API 和前端开发周期。

## 14. 最终产品边界

裁剪后，Ami Brain 仍应坚持三条底线：

1. 事实必须真实：不能因为追求通过率而改 Gold 迎合错误答案。
2. 权限必须可靠：角色、门店、敏感数据和写操作不能进入宽松快速通道。
3. 发布必须可追溯：正式激活仍需绑定不可变候选、真实运行证据和明确回滚点。

治理要从“每一步都很重”改成“高风险步骤足够重，低风险步骤足够快，所有步骤只做一次”。
