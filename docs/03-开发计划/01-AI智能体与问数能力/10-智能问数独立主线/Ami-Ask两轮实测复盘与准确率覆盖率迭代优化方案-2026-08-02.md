## 一、针对两份历史交付说明的校正

### Annotation 1：34 视图首轮交付

首轮没有通过重复问题或错误语义映射凑题。原 2000 题库只能为 25/34 个视图提供至少 10 道合格题，32/34 个视图至少有 1 道合格题，最终真实执行 286 道唯一题，距离 34×10 的发布覆盖少 54 道。

此前回复提到的 `Ami-Ask-34视图问题集实测报告-2026-08-02.xlsx` 当前仓库中不存在，不能作为交付证据。首轮可核验产物为 Markdown 报告、JSON 选题 Manifest 和逐题结果。后续报告统一以 Markdown 总结、JSON 原始结果和 CSV 逐题明细为正式证据；如产品侧确需 Excel，再从冻结 CSV 生成，不反向修改原始结果。

### Annotation 2：650 题第二轮交付

第二轮完整产物已经纳入本次复盘：650 题逐题分类 CSV 共 651 行（含表头）、85 道正式真实执行 JSON、选题 Manifest 和 Markdown 报告。

650 题并非全部适合发送给自由 SQL。管理端/后台暂不支持、Ask 未开放、Brain 建议、写操作、敏感信息、缺少实体和多轮上下文均已独立分类，不能为了提高题数把它们混入 SQL 准确率分母。

## 二、结论先行

### 2.1 两轮结果不能直接比较为版本提升

第一轮 286 题与第二轮 85 道真实执行题标准化后重合数为 0，视图分布和问题难度也不同。因此不能用 `72.94% - 56.3%` 宣称准确率提升了 16.64 个百分点。

两轮测试的价值分别是：

- 第一轮暴露“34 个视图是否都能被正确召回”的基础路由问题。
- 第二轮暴露真实岗位口语、产品边界、管理端事实缺口和组合口径问题。

### 2.2 当前瓶颈已经从“选不到视图”转向“回答合同和发布证据”

在 Holdout v3 形成时的统一 Gold 中，429 道事实查询和 135 道已知歧义题的离线语义评测均为 100%；模型回退候选率为 3.73%，当时确定性语义路由 P95 为 1.182ms。全新独立 Holdout v3 首次冻结后：

- 总计 151 道，与旧题泄漏 0。
- 34 道可查询题的指标和允许视图 Top1、Recall@4、Plan 有效率均为 100%。
- 但 Gold 输出/粒度只有 73.53%。
- 60 道必须澄清题的澄清保留率为 85%，槽位准确率为 80%。

这说明当前优先级不应继续停留在“补更多关键词”，而应转向：

1. 结果形态和必需字段。
2. 多槽位精准澄清。
3. Query Plan 的粒度、排序、比较和完整性。
4. 回答是否真正回应用户问题。
5. Provider 可用性和长尾耗时。

v3 暴露问题修复后，同一题集查询计划和澄清回归均达到 100%，模型回退为 0；但该结果已经属于开发回归，不能再称为“首次未见泛化结果”。Holdout v4 随后按 80 查询、50 澄清、50 边界冻结并完成首次未见评测：首次结果明显未达标，修复后回归才达到查询 80/80、必须澄清 49/49和真实 E2E 80/80。首次结果与修复后结果严格分开，禁止用最终 100% 覆盖首次泛化失败。历史合同误判与最终 checksum 340 题暴露的新校验缺陷共同证明：当路由和 SQL 趋于稳定后，评测合同的假阳性、Validator 的假阴性和执行链路可用性会直接决定报告是否可信。

### 2.3 36 视图覆盖已经完成，业务问题覆盖仍不足

Coverage R2 发布 Manifest 已实现 36/36 视图各至少 10 道真实题，共 360 道；新增能力为库存周转与补货事实、供应商报价与商业条款。当前缺口不再是“每个视图有没有题”，而是剩余管理端高频问题中有多少拥有完整后台事实、能够被安全准确回答。

对第二轮中 234 道“管理端/后台已有相邻能力，Ask 未开放”的逐题审计结果为：

| 分类 | 题数 | 产品处理 |
|---|---:|---|
| 现有 Ask 已可直接承接 | 23 | 补真实口语回归，不新增底层事实 |
| 已有事实，只需补指标/Query Plan | 52 | 原审计候选；二审后 50 道保留并验收 |
| 已有事实，需要新 Ask 语义视图 | 62 | 覆盖率 P1，按能力簇分批开放 |
| 后台事实闭环不完整 | 43 | 先建设业务事件和历史事实 |
| Brain 建议、预测或内容 | 26 | 分流独立 Ami Brain |
| 写操作 | 2 | 保持 Ask 只读，转受控业务流程 |
| 敏感或依赖上下文 | 26 | 精准澄清或拒绝，不扩大敏感字段 |

在当前后台事实条件下，可安全建设的理论上限是 137/234（58.55%），不是 234/234。

2026-08-03 对原 52 道“已有事实、只需补指标/Query Plan”清单完成二次审计和显式合同治理。其中 50 道保留为当前 Ask 可查事实，另 2 道因需新视图、后台事实或澄清而移出当前分母。50 道真实 E2E 复测结果为 50/50：目标视图、SQL Ready、Guard、数据库执行和最终回答均为 100%，平均 12.841 秒，P95 22.499 秒，无数据率 56%。

治理前的典型错误包括：

- “下午两点那个客人想做什么项目”必须返回预约时间、脱敏客户和项目，不能仅校验 `reservation_count`。
- “我们现在有什么产品可以卖”必须返回可售商品列表、商品身份和库存，不能仅校验单个 `current_stock`。
- “今天哪个美容师可以接新单”必须返回员工身份与可用产能，不能只有门店级排班分钟。

因此，原先“直接支持 23 道 + 扩展 52 道 = 75/234”的算法已被实测结果否定。完成库存周转、供应商报价和反馈名单轻量合同后，最新严格管理端覆盖审计为：当前直接可回答 89/234，后台事实可安全开放 135/234，仍属于事实不完整或产品边界的 99/234。不得为达成旧 KPI 将 Brain、写操作、敏感信息或不存在的后台事实强行纳入自由 SQL。

### 2.4 当前产品判定

Ami Ask 当前应判定为“36 视图 Accuracy R1、管理端现有事实 Coverage R1、库存周转与供应商报价两个 Coverage R2 能力簇、反馈名单轻量合同和 Holdout v4 技术回归已完成开发环境验收，但全部 Coverage R2、独立人工签署和生产最小权限验收尚未完成”：

- 最新 Coverage R2 离线语义评测为 450/450；指标、允许视图、必需视图、受控 Query Plan 和严格 Route/Plan 合同均为 100%，136 道真实歧义保留率和槽位准确率均为 100%，无理由澄清率 0，fallback eligible 3.33%，P95 0.928ms。
- 最新发布 Manifest checksum 为 `c8ad3f376b236f38898045f104ea4b6a6c802bd30e5b4949576ccf3e7f217cd2`，连续 360 题严格通过 360/360；Provider、SQL Ready、Guard、数据库执行、Gold Plan 和最终回答正确率均为 100%。
- 360 题平均 8.494 秒，P50 6.960 秒，P95 18.979 秒，达到不高于 22 秒的性能门禁；历史失败题 `manager-004` 和 `BQ0128` 均由受控 fallback 恢复通过，后者耗时 34.213 秒，长尾继续单独披露。
- 管理端 50 题使用当前 Gold 身份重新生成 Manifest 后完整复跑 50/50；平均 9.585 秒，P50 6.478 秒，P95 20.461 秒，无数据率 44%。该 50 题是高频事实回归集，不替代 36 视图发布覆盖。
- Holdout v4 已完成冻结、首次未见、修复后离线回归和最终真实 E2E；首次未见失败历史继续保留，当前独立人工签署状态仍为 `pending`。
- 最新源码重新完成后端与前端构建；7 类真实角色、跨店伪造请求、审计、管理员/普通用户 SQL 可见性均已验收，管理员目录 36 项、库存供应目录 9 项。
- 语义路由关闭可恢复旧候选选择器；自由 SQL 关闭可恢复固定模板。
- 启动最新统一后端时，Ami Brain Active Release 预热曾因共享数据库连接超时导致进程退出。Ask 独立验收实例通过已有 `BRAIN_RELEASE_PILOT_MODE=true` 跳过 Brain 预热后启动；这属于统一进程的启动耦合风险，不计入 Ask 查询准确率，也不能表述为 Brain 已通过。
- 生产专用只读连接和 36/36 最小权限验收仍未完成；`development_admin` 只是开发环境真实功能证据。

因此，下一步不再重复修补当前 Gold。Coverage R2 继续按能力簇建设商品/项目毛利、折扣退款、客户级营销响应、员工效率和客户/预约联合快照；供应商报价能力已完成，不再列为待实施。Holdout v4 独立人工签署、统一进程启动解耦评审和生产只读门禁保持为独立发布门禁。

### 3.3 合并基线的正确用法

- 两轮共 371 道不重复真实问题，原始严格通过 223 道，描述性合并通过率为 60.11%。
- 该数字只代表改造前的问题基线，不代表当前版本准确率。
- 数据库执行成功率不能代替业务答案正确率。
- 正确澄清是成功结果，不应作为 SQL 失败；无理由澄清才是缺陷。
- `development_admin` 只能作为开发真实数据证据，不能作为生产最小权限证明。

## 五、第一性原理：什么才算问数正确

一个问题只有同时满足以下七层，才能计为最终正确：

```text
问题属于 Ask 且当前用户有权限
→ 指标、维度、时间、实体、答案形态解析正确
→ 必需视图全部进入权限过滤后的候选
→ Query Plan 的字段、粒度、过滤、排序和关联正确
→ SQL 通过 Guard、只读事务和单门店限制
→ 数据库结果符合治理口径
→ 最终回答完整、有据、无越界推断并披露必要假设
```

后续报告必须拆分以下指标，禁止用“链路通过率”代替业务准确率：

1. 产品边界分类准确率。
2. 指标 Top1、允许视图 Top1、必需视图 Recall@4。
3. 实体解析准确率和澄清槽位准确率。
4. Query Plan 合同匹配率。
5. SQL Ready、Guard、数据库执行成功率。
6. 最终回答 grounding、完整性和业务正确率。
7. Provider 可用率。
8. 语义、生成、Guard、执行、回答和总链路耗时。

## 六、两轮测试的根因复盘

### 6.1 P0：评测合同曾允许“有数但答非所问”

过去偏重视图命中、SQL 可执行和数字有据，没有强制答案形态、必需字段、排序方向、时间粒度和对象身份。

典型问题是“今天下午最后一个预约是几点，是谁”：如果合同错误地要求预约数量，返回 `reservation_count=0` 也可能被自动判通过。说明评测标准和产品代码必须一起治理。

这不是历史假设：最新发布级运行中，“有没有什么产品只剩最后几瓶了”已实际出现同类假阳性。合同只要求 `current_stock` 标量，导致“低库存商品总库存”被判为回答了“具体哪些商品”。

### 6.2 P0：结果形态比视图路由更容易成为新瓶颈

Holdout v3 首次结果中，指标和视图路由均为 100%，但输出/粒度只有 73.53%。主要风险包括：

- “有几个”被处理为列表或分组。
- “有哪些”被处理为汇总数。
- “排行/最高/最稳定”缺少排序指标和 Top N。
- “比较”缺少双方、差额或变化率。
- “趋势”缺少多个时间点或时间粒度。
- “最后/第一/下一个”缺少排序和 `LIMIT 1`。

### 6.3 P0：澄清必须一次补齐全部关键槽位

“双十一退款率正常吗”同时缺少年份和“正常”的阈值。只问一个槽位会导致用户补充后仍无法执行。

可使用治理默认值的表达应直接查询并披露假设，例如最近 30 天、默认前 10、库存临期 30 天；会实质改变经营结论的缺失条件必须澄清。

### 6.4 P0：高置信唯一指标不应被模型回退改写

`frontdesk-029` 表明，即使问题已唯一命中预约指标，只要分差或阈值配置不稳，仍可能进入模型回退，继而被模型改变结果形态。

原则：高置信、唯一指标、已授权首选视图和完整时间条件同时满足时，路由、答案形态和目标视图应冻结，模型不得改写。

### 6.5 P1：实体和事件的主次关系仍需对抗测试

“预约某项目的客户”应以预约事件为主，项目是过滤条件，客户是输出维度；不能因为同时出现“项目”和“客户”就路由到项目目录或客户档案。

客户、员工、项目、商品和供应商均应先解析稳定 ID；同名或不存在时精准澄清，禁止用脱敏姓名模糊匹配。

### 6.6 P1：业务覆盖缺口不是语义路由能单独解决

234 道管理端相邻问题中，原审计有 52 道看似可通过现有事实补指标解决，二审和真实 E2E 后确认为 50 道。另有 62 道需要新语义视图，43 道后台事实本身不完整。继续堆提示词无法产生不存在的签到、等待、优惠核销、现金流、报销、质检或供应商资质历史。

### 6.7 P1：Provider 和性能需与业务错误分开治理

最终 checksum 完整 340 题的 Provider 可用率为 98.82%，4 项 Provider 失败已经影响最终正确率。其中包括连续不可用、SQL 修复阶段不可用和 circuit open 后立即失败。Provider 错误必须与产品、Gold、数据和安全错误分层统计，不得回填为通过。

最终 checksum 首次完整运行的 P95 曾为 25.959 秒，比 22 秒目标高 3.959 秒。后续已通过 circuit-open 独立 fallback、结构化传输受控重试、只读连接瞬时重试、回答样本压缩和确定性回答兜底，先降至 18.994 秒；最终合同与公共链路收口后的当前完整 340 题 P95 为 21.059 秒，仍满足不高于 22 秒门禁。优化过程中未放宽 Guard、减少必要字段或隐藏失败。

## 九、独立 Holdout v4 设计

为避免再次出现“修完旧题就等于泛化”的错觉，下一轮保留集建议冻结不少于 180 道：

| 必须澄清 | 50 | 覆盖阈值、年份、同名实体和多槽位缺失 |
| Ask/Brain/操作/敏感边界 | 50 | 验证正确分流和拒绝 |

采样要求：

- 不从现有 Gold 做简单同义改写。
- 优先来自真实岗位口语、倒装句、简称、错别字、实体+事件组合和跨期比较。
- 每个问题有唯一 ID、来源、checksum 和人工双审合同。
- 冻结后不得修改题目或合同；错误通过追加裁定账本处理。
- 首次结果用于泛化结论，修复后结果只作为开发回归。
