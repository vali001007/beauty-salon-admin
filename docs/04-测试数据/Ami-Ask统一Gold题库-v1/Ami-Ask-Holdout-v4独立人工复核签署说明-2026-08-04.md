## 三、复核流程

1. 产品复核人在“产品复核结论”选择“通过 / 需修正 / 不适用”，并填写独立的产品复核人和日期。
2. 技术复核人独立填写技术结论、技术复核人和日期；产品复核人与技术复核人的人员集合必须全局分离，不能在不同题目中交换角色规避独立复核。
3. 任一方选择“需修正”时，必须填写备注，并另行追加裁定条目；不得覆盖冻结合同和首次结果。
4. 180题产品和技术双审全部完成后，复核人填写姓名和日期。
5. 最终追加一条签署记录，记录冻结合同 checksum、首次结果 checksum、裁定账本 checksum、复核人、日期和通过/不通过结论。

### 3.1 机器校验与签署记录

完成工作簿后，将“逐题复核”工作表导出为 UTF-8 CSV，在 `packages/server-v2` 运行：

```bash
npm run ask-data:free-sql:holdout-human-signoff -- --input=/absolute/path/holdout-v4-review.csv
```

校验器强制检查：

- 180题不少题、不重复、不混入未知 Case ID。
- 每题合同 checksum 与冻结 JSON 一致。
- 产品和技术结论均为“通过”，姓名和 ISO 日期齐全。
- 产品和技术复核人集合全局独立；同一人员不得在任意题目中同时承担两类复核角色。
- “需修正 / 不适用”必须有备注，且不允许生成已批准签署。
- 复核日期合法、不得早于 Holdout 合同冻结日期，也不得位于未来。
- 严格命令行校验失败时必须返回非零退出码；已存在的签署记录禁止覆盖。

门禁自动合同已通过 11/11，包含待复核材料的严格拒绝和签署记录只追加验证；该组合同已纳入 `npm run ask-data:free-sql:test` 主回归入口，避免 CI 或后续开发漏跑。

校验通过后才可显式生成一个新的只追加签署记录：

```bash
npm run ask-data:free-sql:holdout-human-signoff -- \
  --input=/absolute/path/holdout-v4-review.csv \
  --write-record=../../docs/04-测试数据/Ami-Ask统一Gold题库-v1/Ami-Ask全新独立Holdout-v4人工签署记录-YYYY-MM-DD.json
```

输出路径已存在时脚本会拒绝覆盖；脚本不修改冻结合同、首次结果或裁定账本。

## 四、签署完成条件

只有同时满足以下条件，才可将 `independentHumanSignoff` 从 `pending` 改为已签署：

- 180/180 产品复核已完成。
- 180/180 技术复核已完成。
- 产品和技术复核身份分开，机器校验通过。
- 所有“需修正”均有明确理由和只追加裁定。
- 复核人不是本轮题库生成、自动裁定或代码修复的唯一执行者。
- 签署结论明确保留“首次未见未达标”和“P95 40.622秒”两项事实。
